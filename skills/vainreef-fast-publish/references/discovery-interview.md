# Creative Requirement Discovery

## Purpose

帮助用户把一个朦胧想法逐轮发展成清楚、完整、可确认的 App 设想。创意提问与工程思考同步进行：先问“想做什么”，每轮探索画面、玩法和体验，同时观察性能、联网、权限、依赖和发布工作量。

## First question

用户还没有描述具体想法时，使用：

```text
你想做一个什么样的 App？可以先随意描述你脑中的画面、玩法或感觉。
```

用户已经给出想法时，先创建 living README，再从最有创意价值的缺口继续提问。

## Core loop

每轮严格执行：

```text
接收回答
→ 阅读当前 README
→ 更新“需要 / 暂时省略 / 新创意 / 已确定 / 待明确”
→ 检查性能、联网、权限、依赖、商业化与发布影响
→ 有实质风险时写入提醒并向用户确认方向
→ 记录用户的实现方向选择
→ 保存 README
→ 判断用户是否准备收口
→ 继续时只问一个最自然的问题
```

### 对用户可见的语言规则

语言规则与 SKILL.md「对用户的语言规则」一致：用户只理解日常语言，说给用户听的每一句话不得出现内部术语或工程名词。访谈阶段特别留意：项目名、存储方式、框架名一律用日常表达（"记下日子""系统会弹一条通知"）。

### README update rules

- 用户明确想要的内容写入“用户需要什么”。
- 用户明确排除、推迟或兴趣较低的内容写入“用户目前不需要什么”。
- 仍在想象、尚未确认的点子写入“正在探索的创意”。
- 用户明确认可的内容移入“已经确定”。
- 新答案替代旧答案时，以新答案更新正文，并在创意记录中写清变化。
- 用户表达“其他部分你决定”时，记录为“交给 Agent 发挥”，后续依据整体风格补全。
- 每轮保存日期/轮次、本轮新增、本轮调整、本轮移除和一句用户原意摘要。
- 发现明显工程影响时更新“当前考虑与提醒”；用户选择后更新“用户的实现方向选择”。
- README 始终反映当前最新理解，而创意记录保留演变轨迹。
- 用户表达“过完就隐藏”“不要了”“旧的不用管”这类数据清理倾向时，主动确认一句：“藏起来以后想找还能找到；完全不想要的，要不要能直接删掉？”——隐藏不等于删除，删除能力在访谈中确认后写入 README。
- 用户需求涉及“提醒我”“弹通知”“定时”“开机启动”这类系统行为时，先说明日常影响：“到时候系统会弹一条通知，需要在系统设置里允许这个应用发通知”，再确认是否保留该功能。

## Adaptive defaults

将 Progressive Discovery 视为“少问、高价值、持续记录”：

- 能从用户第一句话安全推断的内容采用合理默认值，并把默认值写进 README。
- 只有以下情况才提问：会显著改变用户体验；会明显改变工程规模或发布路径；存在两个以上明显不同的合理方向；或用户主动表现出犹豫。
- 默认值要用一句话告诉用户，例如：“我先按拖入文件、调整顺序、保存结果来理解；你有特别想要的玩法再告诉我。”
- 默认值不锁死创意，用户补充后立即更新正文与创意记录。
- 每轮更新 README 仍然保留，问答次数随需求复杂度动态变化。

## Progressive question ladder (choose only the needed layer)

问题按用户回答动态选择；每轮优先一个问题。

### Layer 1 — What do you want to make?

目标：让创意自由展开。

- 你脑中最想做的是一个什么 App？
- 你想象它打开时是什么画面？
- 这个想法里，最让你兴奋的是哪一部分？
- 如果今天就能用上，你最想先体验什么？

### Layer 2 — Who and when?

目标：建立使用画面。

- 你想主要自己用，还是也希望别人会喜欢？
- 人们通常会在什么时候打开它？
- 是每天都会打开，还是某个场景下才会想到它？
- 使用时，人通常正在做什么？

### Layer 3 — What happens after opening?

目标：把想法变成具体体验。

- 打开后第一眼最应该看到什么？
- 用户第一步会点哪里、输入什么或放进去什么？
- 接着你希望发生什么？
- 最后用户会得到什么、看到什么或保存什么？
- 哪个瞬间最应该让用户觉得“就是这个”？

### Layer 4 — Explore the creative possibilities

目标：扩展、比较和选择创意。

- 怎样让这个过程更有趣、更漂亮或更有仪式感？
- 你希望它主动给建议，还是完全听用户操作？
- 有没有一个小惊喜、动画、声音或文案会让它更有记忆点？
- 如果加入一个你原来没想到的功能，你最希望它往哪个方向发展？
- 哪种做法会让它太复杂或失去原来的感觉？

### Layer 5 — Wants and current exclusions

目标：明确当前版本的取舍。

- 第一版你最想保留哪三件事？
- 有哪些东西你明确希望当前版本先省略？
- 哪些点子很喜欢，但更适合以后再加入？
- 哪些体验一旦改变，就不再是你想做的那个 App？

### Layer 6 — Product behavior in everyday language

目标：用日常场景补足当前轮的可行性判断，同时保持低思维负担。

- 这些内容只要留在当前电脑里，还是希望换电脑后也能看到？
- 大家是否需要自己的登录身份？
- 它是否需要从网上获取内容，还是主要使用用户自己放进去的东西？
- 多个人之间是否要共享同一份内容？
- 用户是否会用到自己的照片、文件、声音或位置？
- 第一版是否确定让大家免费使用？

只在用户的想法涉及对应行为时提出这些问题；使用场景描述代替工程术语。

### Layer 7 — Name, mood, and personality

目标：确定产品气质。

- 你想暂时叫它什么？
- 希望它给人的感觉是安静、专业、可爱、有趣、酷，还是别的？
- 有喜欢或想避开的颜色、语言风格、图标感觉吗？
- 第一次打开时，最希望它对用户说什么？

### Layer 8 — What counts as “this is it”?

目标：形成用户自己的完成标准。

- 这个 App 做到什么程度，你就觉得“行了，做好了”？
- 最重要的一次完整体验应该是什么？
- 第一版做完以后，你最想马上演示给别人看的是什么？

如果用户对提问没反应或反问“什么？”，立即停止追问，换一句更简单的说法，例如：“你希望它做到什么程度就算做好？比如'能加日子、日期算得准、会提前提醒，这样就够了'？”不要重复原问法，也不要解释提问的用意。

## Continuous feasibility lens

每轮回答后，Agent 在内部检查以下信号：

| 信号 | 需要当轮提醒的情况 | 面向用户的解释重点 |
| --- | --- | --- |
| 技术栈适配 | 完整 3D 游戏、重度实时渲染、复杂物理、专业视频编辑等 | 当前路线擅长的产品类型，以及继续后对画面、性能、稳定性的影响 |
| 规模 | 大地图、大量同时对象、超大媒体文件、持续后台处理 | 第一版的响应速度、机器负担和测试范围 |
| 在线能力 | 实时多人、统一账号、云同步、共享数据、持续在线服务 | 应用需要长期依赖另一套在线系统 |
| 项目方秘密 | 所有用户共享项目方充值的调用额度 | 安装到用户电脑后的信息保护与费用控制 |
| 系统访问 | 管理员、驱动、内核、全局拦截、深层磁盘访问 | 对用户电脑的影响和商店审核变化 |
| 系统提醒 | 通知、弹窗、定时提醒、后台触发 | 需要在系统设置允许通知；先说明“到时候系统会弹一条通知”，再确认方向 |
| 商业化 | 付费、订阅、广告、内购、许可证 | 额外的付款、结算与发布步骤 |
| 平台目标 | 同时要求手机、网页、Mac、Linux | 当前路线聚焦 Windows，多个平台会形成另一套产品工程 |
| 行业前提 | 金融、医疗、赌博、特殊版权或组织资格 | 上架前需要额外证明、规则和资料 |

### Design impact protocol

发现明显工程影响时：

1. 更新 README 的“当前考虑与提醒”。
2. 用一段简短语言说明用户目标、主要工程量和发布影响。
3. 给出一到两个实现方向，也保留用户原方向。
4. 询问用户更偏好哪一种产品体验。
5. 把选择写入 README，然后继续探索或制作。

通用表达：

```text
这个想法里有一处值得先选方向。
你想要的是：[用户体验]。
按完整规模制作会增加：[画面 / 性能 / 稳定性 / 发布复杂度]。
可以按原方向继续，也可以先采用：[方向 A] 或 [方向 B]。
你更喜欢哪一种成品体验？
```

3D 射击示例：

```text
完整 3D 射击游戏会同时涉及实时 3D 画面、角色动画、物理碰撞、地图、音效和持续性能优化。
可以直接按完整版本设计，也可以先做轻量 2D、俯视角射击或射击训练版本。
你更希望第一版呈现哪一种体验？
```

README 记录用户选择、实现方向与制作中需要验证的事项；后续发现新的实质影响时补充说明。

## Stop-signal detection

用户可以在任意一轮结束创意阶段。按语义识别，不依赖固定句子。

常见信号：

- 就是这样、差不多、就这些。
- 这个方向可以、按这个来。
- 开始吧、可以做了。
- 第一版先这样。
- 其他你决定、暂时没有补充。

收到信号后：

1. 更新 README 并保存本轮记录。
2. 停止新增创意问题。
3. 阅读 README 全文，以最新表达为准整理重复与变化。
4. 输出完整的产品复述。
5. 结尾询问：`我理解的是这样，对吗？`

## Plain-language confirmation

确认复述只包含产品体验：

- 这是一个什么 App。
- 谁会使用、什么时候使用。
- 打开后第一眼看到什么。
- 用户依次做什么、最后得到什么。
- 用户需要什么。
- 用户目前不需要什么。
- 它应该带来什么感觉。
- 第一版怎样算做好。

此时隐藏工程名称、框架名称、编程语言、存储方式、服务名称、权限名称、安装包与发布工具。把访谈中已经确认过的调整翻译为产品体验，例如“第一版采用俯视角射击”，无需再次展开工程解释。

确认模板：

```text
我理解你想做的是：

[用两三句话描述整个 App。]

使用时会是这样：
1. [打开后的画面]
2. [用户的主要动作]
3. [接下来发生的事情]
4. [最终得到的结果]

你需要的：
- [需要 1]
- [需要 2]
- [需要 3]

你目前想省略的：
- [省略 1]
- [省略 2]

整体感觉：[风格和体验]
第一版做好时：[用户自己的完成标准]

我理解的是这样，对吗？
```

## Transition to implementation

用户回答“对”“就是这样”或表达等价确认后：

1. 更新 README 状态为“需求与可行方向已确认”。
2. 保存确认时间和最终产品复述。
3. 检查所有重要提醒均有用户选择；仍待制作验证的内容清楚记录。
4. **输出双窗口并行非阻塞提示**：
   ```text
   我已开始为你全自动编写代码、生成界面、打包并进行自动化测试（大约需要 15~20 分钟）。
   这段时间如果你想提前准备微软开发者账号，可以随时新开一个对话窗口向我提问：“我要如何创建 Partner 开发者账号？”，我会指引你完成免费个人认证。发布时的名称验重、建项与商店提审将由工具链全自动完成。
   ```
5. **构建主会话专心执行工程流水线**，保持专注，直到打包安装完成并邀请用户试用。

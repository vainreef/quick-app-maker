# 需求访谈与方案协同规范

## 核心原则与硬约束（防逃逸铁律）

1. **感性形容词绝对不等于充分信息**：
   - 当用户仅给出单句、意向性或感性描述（如“我有重要的事情想要记住，打开有仪式感”、“想做一个极简清爽的记账工具”）时，**严禁**自作主张判定为“信息充足”并直接开工！
   - 感性词（如“仪式感”、“有格调”、“高级感”）必须被具象化为具体的**物理实体载体、视听动效与操作交互**。

2. **具象化 A/B 方案引导法（禁止干瘪盘问，提供生动选择）**：
   - 面对抽象描述，严禁向用户抛出冰冷的技术或生硬的填空式提问（如“请问你的数据结构是什么？你需要哪些字段？”）；
   - Agent 必须基于用户的抽象愿景，主动构思并提出 **2 个具有鲜明体验差异、高质感的具象化落地产品方案**（例如：方案 A 偏向火漆印章卡片式仪式感；方案 B 偏向时间胶囊倒数日式仪式感）；
   - 方案中说明各自的**核心视觉、第一眼操作体验、建议中文名**，交由用户二选一或在此基础上提出偏好。

3. **停步等待（Human-in-the-Loop）强制闭环**：
   - 抛出 A/B 方案后，Agent **必须结束当前发言，从容等待用户回复**；
   - **绝对严禁**在同一条回复中自问自答、自定方案并直接调用 `create` 或编写代码；
   - 只有当用户明确回复（如“选方案 A”、“想要印章那种风格”或补充了具体的交互细节）后，方可进入工程创建阶段。

4. **技术黑话绝缘墙**：
   - 严禁向用户提及 `slug`、`脚手架`、`Vue`、`Electron`、`IPC`、`main.cjs`、`CSS` 等任何内部代码术语；
   - 英文目录名（slug）由 Agent 内部自动推导（如应用定名为「时光印记」，自动推导 `time-seal`）。

## 抽象需求应对范式（实战示例）

### 典型场景：用户仅说了一句感性意向
> **用户**：“我有重要的事情，想要记住，打开有仪式感。”

#### 错误做法（严禁）：
> **Agent**：“好的，信息已经充足，我将为您创建一个带有仪式感的记事应用并开始编写代码……”（❌ 严重违反铁律，剥夺用户参与感，极易做出完全不对齐的垃圾产物）

#### 正确做法（标准引导话术）：
> **Agent 回复**：
> “记重要的事情确实需要特别的郑重感和沉浸感！针对你想要的‘仪式感’，我为你构思了两种截然不同的体验方案，看看你更喜欢哪一种：
>
> - **方案 A：『时光火漆印』**
>   - **仪式感体验**：深黑胡桃木纹理质感，每当你写下一个重要承诺或重大决定，点击保存时会伴随一枚专属金色火漆印章缓缓盖下的视听动效与专属编号，如同签下一份庄重的契约；
>   - **日常浏览**：以典雅手帐卡片形式陈列，支持翻阅和封存归档；
>   - **建议名称**：时光印记。
>
> - **方案 B：『星辰时间胶囊』**
>   - **仪式感体验**：深邃夜空星光界面，输入重要事项并设定启封时刻，保存时化作一颗悬浮的星芒胶囊，在打开前保持密闭封存，带来等待与揭晓的庄严感；
>   - **日常浏览**：星系轨迹陈列，重要倒计时跃然眼前；
>   - **建议名称**：星语胶囊。
>
> 你更中意哪种感觉？或者你有其他特别的画面偏好，告诉我后我们马上动手制作！”
>
> *(Agent 结束发言，等待用户回复)*

## 需求准出核对清单（Checklist）

在进入 `qam create` 之前，必须在上下文中有明确证据满足以下条件：

- [ ] **形态载体已明确**：用户已确认或指定了具体的界面载体（如：印章契约、手帐卡片、时间胶囊、清单表格等）；
- [ ] **核心操作已明确**：明确了用户打开应用后的“第一眼”和“一次最核心的操作行为”；
- [ ] **中文名称已敲定**：已有清晰或暂定的中文产品名称（便于内部推导 slug）；
- [ ] **用户已明确回复确认**：用户至少发出了一条明确确认意向的回复（如“方案A”、“就叫时光印记”）。

满足上述条件后，输出简短确认句并立即启动静默业务开发与测试：
> “收到，就按【方案名称】为你全力打造！我现在在后台为你完成应用的开发与调试，完成后直接在屏幕上为你打开试用体验。”

# Creative Requirement Discovery

## Purpose

帮助用户把一个朦胧想法逐轮发展成清楚、完整、可确认的 App 设想。第一阶段是创意空间：先问“想做什么”，通过连续追问探索画面、玩法、体验与边界。可行性分析放在用户确认整个产品之后。

## First question

用户还没有描述具体想法时，使用：

```text
你想做一个什么样的 App？可以先随意描述你脑中的画面、玩法或感觉。
```

用户已经给出想法时，先创建 living README，再从最有创意价值的缺口继续提问。

## Core loop

每轮严格执行：

```text
接收回答
→ 阅读当前 README
→ 更新“需要 / 暂时省略 / 新创意 / 已确定 / 待明确 / 本轮记录”
→ 保存 README
→ 判断用户是否准备收口
→ 继续时只问一个最自然的问题
```

### README update rules

- 用户明确想要的内容写入“用户需要什么”。
- 用户明确排除、推迟或兴趣较低的内容写入“用户目前不需要什么”。
- 仍在想象、尚未确认的点子写入“正在探索的创意”。
- 用户明确认可的内容移入“已经确定”。
- 新答案替代旧答案时，以新答案更新正文，并在创意记录中写清变化。
- 用户表达“其他部分你决定”时，记录为“交给 Agent 发挥”，后续依据整体风格补全。
- 每轮保存日期/轮次、本轮新增、本轮调整、本轮移除和一句用户原意摘要。
- README 始终反映当前最新理解，而创意记录保留演变轨迹。

## Progressive question ladder

问题按用户回答动态选择；每轮优先一个问题。

### Layer 1 — What do you want to make?

目标：让创意自由展开。

- 你脑中最想做的是一个什么 App？
- 你想象它打开时是什么画面？
- 这个想法里，最让你兴奋的是哪一部分？
- 如果今天就能用上，你最想先体验什么？

### Layer 2 — Who and when?

目标：建立使用画面。

- 你想主要自己用，还是也希望别人会喜欢？
- 人们通常会在什么时候打开它？
- 是每天都会打开，还是某个场景下才会想到它？
- 使用时，人通常正在做什么？

### Layer 3 — What happens after opening?

目标：把想法变成具体体验。

- 打开后第一眼最应该看到什么？
- 用户第一步会点哪里、输入什么或放进去什么？
- 接着你希望发生什么？
- 最后用户会得到什么、看到什么或保存什么？
- 哪个瞬间最应该让用户觉得“就是这个”？

### Layer 4 — Explore the creative possibilities

目标：扩展、比较和选择创意。

- 怎样让这个过程更有趣、更漂亮或更有仪式感？
- 你希望它主动给建议，还是完全听用户操作？
- 有没有一个小惊喜、动画、声音或文案会让它更有记忆点？
- 如果加入一个你原来没想到的功能，你最希望它往哪个方向发展？
- 哪种做法会让它太复杂或失去原来的感觉？

### Layer 5 — Wants and current exclusions

目标：明确当前版本的取舍。

- 第一版你最想保留哪三件事？
- 有哪些东西你明确希望当前版本先省略？
- 哪些点子很喜欢，但更适合以后再加入？
- 哪些体验一旦改变，就不再是你想做的那个 App？

### Layer 6 — Product behavior in everyday language

目标：补足以后做可行性判断所需的产品事实，同时保持低思维负担。

- 这些内容只要留在当前电脑里，还是希望换电脑后也能看到？
- 大家是否需要自己的登录身份？
- 它是否需要从网上获取内容，还是主要使用用户自己放进去的东西？
- 多个人之间是否要共享同一份内容？
- 用户是否会用到自己的照片、文件、声音或位置？
- 第一版是否确定让大家免费使用？

只在用户的想法涉及对应行为时提出这些问题；使用场景描述代替工程术语。

### Layer 7 — Name, mood, and personality

目标：确定产品气质。

- 你想暂时叫它什么？
- 希望它给人的感觉是安静、专业、可爱、有趣、酷，还是别的？
- 有喜欢或想避开的颜色、语言风格、图标感觉吗？
- 第一次打开时，最希望它对用户说什么？

### Layer 8 — What counts as “this is it”?

目标：形成用户自己的完成标准。

- 你亲自打开它时，哪几件事做到就会觉得“这就是我想要的”？
- 最重要的一次完整体验应该是什么？
- 第一版做完以后，你最想马上演示给别人看的是什么？

## Stop-signal detection

用户可以在任意一轮结束创意阶段。按语义识别，不依赖固定句子。

常见信号：

- 就是这样、差不多、就这些。
- 这个方向可以、按这个来。
- 开始吧、可以做了。
- 第一版先这样。
- 其他你决定、暂时没有补充。

收到信号后：

1. 更新 README 并保存本轮记录。
2. 停止新增创意问题。
3. 阅读 README 全文，以最新表达为准整理重复与变化。
4. 输出完整的产品复述。
5. 结尾询问：`我理解的是这样，对吗？`

## Plain-language confirmation

确认复述只包含产品体验：

- 这是一个什么 App。
- 谁会使用、什么时候使用。
- 打开后第一眼看到什么。
- 用户依次做什么、最后得到什么。
- 用户需要什么。
- 用户目前不需要什么。
- 它应该带来什么感觉。
- 第一版怎样算做好。

此时隐藏工程名称、框架名称、编程语言、存储方式、服务名称、权限名称、安装包与发布工具。用户确认产品后，另开一个清楚的可行性分析阶段。

确认模板：

```text
我理解你想做的是：

[用两三句话描述整个 App。]

使用时会是这样：
1. [打开后的画面]
2. [用户的主要动作]
3. [接下来发生的事情]
4. [最终得到的结果]

你需要的：
- [需要 1]
- [需要 2]
- [需要 3]

你目前想省略的：
- [省略 1]
- [省略 2]

整体感觉：[风格和体验]
第一版做好时：[用户自己的完成标准]

我理解的是这样，对吗？
```

## Transition to feasibility

用户回答“对”“就是这样”或表达等价确认后：

1. 更新 README 状态为“需求已确认”。
2. 保存确认时间和最终产品复述。
3. 进入 Capability Boundary 分析。
4. 将分析与产品确认分成两条独立消息或两个明显阶段。
5. 若第一版体验需要调整，用生活化语言解释，并询问：`这样调整可以吗？`

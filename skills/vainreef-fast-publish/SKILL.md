# Vainreef Fast Publish V2

使用仓库现有入口完成 Windows 应用制作和 Microsoft Store 发布。保留已经跑通的页面操作与浏览器流程，不临时重写发布控制器。

## 选择模式

根据用户当前目标只进入一个模式：

1. **创建应用**：新建 Windows 桌面应用。
2. **修改应用**：调整已有应用的功能、数据或外观。
3. **准备发布**：整理名称、程序包、文案和图片。
4. **继续发布**：根据当前状态处理尚未完成的商店阶段。

按需读取资料：

- 创建或修改应用：[需求访谈](references/discovery-interview.md)
- 执行现有命令：[命令手册](references/commands.md)
- Microsoft Store 流程与页面操作：[发布手册](references/store.md)
- 已经遇到过的页面、打包问题和图片交付：[发布手册](references/store.md)
- 国内网络和工作区缓存：[网络与缓存](references/network.md)

## 共同约束

- Windows 命令统一通过 `bootstrap/qam.cmd`；工作区中的便携 Node、Git、npm 和缓存保持隔离。
- macOS/Linux 使用仓库现有入口；浏览器选择沿用当前已跑通的配置。
- 自动识别工具仓库、工作区和应用目录。英文目录名由 Agent 内部推导，不向普通用户询问。
- 创建命令只生成基础骨架，随后必须实现用户要求的真实业务。
- 本地状态沿用 `window.qam.loadState()` 与 `window.qam.saveState()`，界面与主进程的数据字段保持一致。
- 同一个应用的开发、打包和 Store 操作严格串行。
- `qam dev` 是长驻进程；Agent 在后台启动并直接向用户展示窗口。
- 页面故障处理只使用发布手册中已经记录的做法。

## 创建或修改应用

1. **需求访谈与方案确认（强制阻断）**：
   - 严禁凭单句意向或感性形容词（如“有仪式感”、“好看方便”）自行脑补并直接判定“信息充足”擅自开工；
   - 用户描述缺少具体交互载体、操作闭环或功能边界时，必须读取并遵循 [需求访谈](references/discovery-interview.md)，提出 2 个具象化落地形态方案供用户选择；
   - 提问后**必须结束当前发言，强制等待用户回复确认**；
   - 仅当用户明确确认了具体产品形态、核心交互与暂定名称后，方可进入工程创建。
2. 创建或定位应用并实现实际业务（严禁保留空骨架，必须实现完整交互与本地持久化）。
3. 运行现有应用测试（`qam test`）。
4. 在真实窗口中完成用户要求的核心操作。
5. 后台保持应用窗口打开，交给用户试用和提出修改意见。

## 发布触发条件

只有用户明确提出上架、发布、打包或继续 Store 提交时进入发布流程。

发布过程保留三个用户确认节点：

1. 用户登录并亲自保留产品名称；
2. 用户选择图片和文案的来源方案；
3. 用户检查全部图片并明确确认继续。

图片视觉效果由用户最终判断。模型具备视觉能力时可以协助生成和整理，但不能替代用户确认；模型缺少视觉能力时直接整理文件并交给用户检查。

## Store 执行原则

- 先读取当前状态，优先处理尚未完成的阶段。
- `store plan` 用于只读查看当前差异；`store apply --phase` 用于执行单个阶段。
- 页面填写沿用当前 Direct-Apply 实现：识别页面类型、填写完整表单、保存并记录检查点。
- 对已经显示完成的阶段避免重复填写。
- 所有阶段处理后运行现有 `store verify` 总检。
- 最终“提交进行认证”由用户在浏览器中亲自执行。

## 用户沟通

- 面向普通用户只说明应用效果、需要准备的材料和下一步操作。
- 登录、双重验证、名称保留、图片确认和最终提交时，给出清晰指引并等待用户回复。
- 用户明确询问仓库、Skill、测试或故障原因时，可以提供必要的文件、状态和验证记录。

## 完成口径

应用完成以现有测试通过、真实窗口可操作并已交给用户试用为准。Store 准备完成以当前发布流程执行完毕、现有总检通过以及用户确认图片为准。不要把新增推断或尚未运行的检查写成完成证据。
